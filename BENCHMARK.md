# Бенчмарк извлечения контента

## Воспроизведение

Запуск из корня репозитория на Node.js 22.23.5 или новее из поддерживаемой ветки LTS. Для полной матрицы понадобится исполняемый файл Obscura из проверяемого коммита. Рекомендованная сопоставимая сборка на том же хосте использует `cargo build --release -p obscura-cli --bins --features render`.

```powershell
Push-Location benchmarks
npm ci --ignore-scripts
node ./node_modules/playwright/cli.js install chromium --only-shell
npm test
npm run benchmark -- --runs 3 --obscura ../target/release/obscura.exe --obscura-revision HEAD
Pop-Location
```

На Linux и macOS используйте путь к `obscura` без `.exe`. Флаг `--obscura-revision` сверяет запрошенный коммит с отметкой в `obscura --version`. Для диагностики на Chromium используйте `--allow-partial` вместо параметров Obscura. Флаг `--split` принимает `development`, `evaluation` или `all`. Playwright запускает headless-сборку Chromium из закреплённой версии пакета. Obscura слушает loopback, а доступ к частным сетям включён для локального сервера fixtures. Оба движка берут страницы и ресурсы с этого сервера.

[Workflow Content benchmark](.github/workflows/content-benchmark.yml) проверяет оценщик на pull request. При отправке бенчмарка в ветку `benchmark/baseline` он собирает `76db0c8`, запускает оба корпуса на одном Linux-хосте и сохраняет отчёты как артефакт. При ручном запуске можно указать коммит кандидата и включить публичный корпус параметром `public_pages`. [Установка Chromium в CI](https://playwright.dev/docs/ci).

## Методика

- Корпус `local-v1` содержит 30 синтетических страниц и размеченные ожидания. 20 страниц отведены для разработки, 10 для оценки. Четыре страницы проверяют динамическое содержимое через таймер, локальный fetch или клик. На страницах есть разное число повторов навигации, а уникальные значимые факты встречаются в боковой панели и подвале.
- Для каждой страницы создаётся новый контекст. Оба движка используют viewport 1280×720 при DPR 1 и ждут DOMContentLoaded, выполняют действие при необходимости и проверяют сигнал готовности страницы. Снимок состоит из `document.documentElement.outerHTML`. Obscura в той же CDP-сессии читает встроенный Markdown через `LP.getMarkdown`.
- A, B, C и X используют один снимок Chromium на страницу и повтор. B использует Turndown + GFM, C добавляет Readability перед тем же конвертером. D измеряет встроенный сериализатор в Obscura. D-raw и D-standard используют его снимок для проверки покрытия движка и общего конвертера. X исполняет конвертер Obscura из проверяемой ревизии над инертным jsdom, восстановленным из Chromium HTML. X измеряет правила сериализации без исполнения сценариев страницы и без участия движка Obscura.
- Текст оценивается по точным ожидаемым фразам после нормализации пробелов. Числовая подметрика покрывает фразы с цифрами. Она проверяет сохранение ожидаемых значений в этих фразах. Оценка структуры проверяет DOM или результат рендера Markdown на таблицы, строки кода, роль цитаты, иерархию, адреса и другие размеченные артефакты. Адреса оцениваются после разрешения относительно URL страницы. Минимальный набор тестов проверяет полноту корпуса и реакцию оценщика на конкретные потери.
- Число входных токенов представления измеряется кодировками `o200k_base` и `cl100k_base`. Сравнение с B использует одинаковые пары «страница и повтор» с успешным извлечением. Полнота учитывает ожидаемые факты всего выбранного набора, а состояние недоступного движка показано отдельно. E и F появятся после подключения общего оптимизатора.
- Записываются версии, хеши корпуса и lockfile, коммит, ОС, оборудование, запуск браузера и времена этапов. Порядок захвата движками меняется по страницам и повторам. Оба процесса переиспользуются в пределах прогона. Время захвата включает создание страницы, навигацию, ожидание, снимок и закрытие страницы, а у D также запрос встроенного Markdown. Время преобразования D соответствует интервалу этого CDP-запроса. Измерения ресурсов, конкуренции, живых сайтов, накладных расходов MCP и выполнения задач с LLM предстоят.

JSON, CSV и краткий Markdown-отчёт сохраняются в `target/content-benchmark` или в папке из `--out`. Детальный JSON хранит исходные утверждения и проверки по каждой попытке, включая статусы ошибок запуска, навигации, готовности, получения снимка и извлечения.

Для сравнения ревизий сохраняйте их в разные папки через `--out`. Из `benchmarks` выполните `npm run compare -- <base.json> <base-config> <candidate.json> <candidate-config>`. Сравнение вернёт изменения в покрытии, подробности потерь и токены на совместно успешных парах. Скрипт сверяет состав прогона, зависимости, версии Node.js и Chromium, платформу и параметры захвата.

Для замера общего конвертера добавьте `--converter <path> --converter-revision <commit>`, передавая отдельный release-бинарник кандидата. Вариант E получает тот же HTML, что B, а F получает тот же HTML, что D-standard. В обоих вариантах команда `obscura content` принимает снимок через stdin. Время преобразования включает запуск процесса CLI. Для первой итерации тот же workflow запускается на ветке `benchmark/structured-markdown`, где используются исходный браузер `76db0c8` и отдельно собранный конвертер кандидата.

Для воспроизведения на поддерживаемой платформе используйте Linux-workflow или другую систему из списка Playwright. [Требования Playwright](https://playwright.dev/docs/intro#system-requirements).

- C расходует на 79,5% меньше `o200k_base` токенов, чем B, и пропускает длительность закрытия и порог бесплатной доставки. B и C теряют показание 12,7 Вт в таблице с объединённой ячейкой. Высокая экономия C отражает в том числе короткие синтетические статьи и повторяющееся меню корпуса.
- X сохраняет размеченные фразы и числовые значения. Проверка структуры выявляет потери в коде, вложенных списках, таблицах, формулах, раскрываемых блоках и метаданных. Размер X превышает B на 0,26% в обеих кодировках.
- На десяти оценочных страницах A, B, C и X сохранили 63/63 факта, а структура различалась: A 27/27, B и C 18/27, X 12/27. Полный набор нужен, чтобы увидеть потери фактов в C.

В Windows-прогоне измерены Chromium и отдельная проверка алгоритма Markdown X. Результаты прямого сравнения с Obscura приведены ниже.

Обновлённый отчёт сохранён в `target/content-benchmark-patched`. Исторический запуск с Chromium 141.0.7390.37 и Node.js 22.12.0 хранится в `target/content-benchmark`. Между ними совпали результаты каждой текстовой и структурной проверки и число токенов по каждой попытке. Замеры производительности следует сравнивать внутри одного набора версий.

## Публичный корпус

`npm run benchmark -- --dataset public --obscura <path> --obscura-revision HEAD` запускается из `benchmarks` и по умолчанию делает один повтор. `--allow-partial` без параметров Obscura запускает Chromium. Список адресов, признаков готовности и проверок хранится в [public-fixtures.mjs](benchmarks/public-fixtures.mjs). Корпус содержит Python, RFC Editor, MDN, arXiv, W3C WAI и Wikipedia.

В режиме `public` Chromium запускается с sandbox, Obscura использует штатное ограничение доступа к частным сетям. Оба движка проверяют идентичность страницы по селектору и тексту после DOMContentLoaded. Неполное или недоступное содержимое отражается в статусах и полноте. Отчёт в `target/content-benchmark-public` хранит момент запуска, адрес, HTTP-статус при наличии и SHA-256 фактического снимка. Скрипт сравнения показывает, сколько пар получили одинаковый снимок. Сайты могут менять содержимое, поэтому этот прогон проверяет совместимость, а воспроизводимость измеряется на локальных fixtures.

В двух локальных прогонах Chromium загрузил все шесть публичных страниц с HTTP 200. Стандартный Markdown сохранил 17 из 17 фактов и 6 из 7 проверок структуры. Readability сократил расход токенов на 20,76% по `o200k_base` и сохранил 15 из 17 фактов и 4 из 7 проверок структуры. Пропущенные факты касаются условий отображения раскрываемого блока и заголовков, охватывающих несколько строк или столбцов. Экономия на синтетическом корпусе составила 79,5%. Доля RFC 9110 в токенах стандартного Markdown публичного корпуса составляет около 67%, поэтому агрегат сопровождается данными по страницам. [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details) · [W3C WAI](https://www.w3.org/WAI/tutorials/tables/irregular/) · [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

При повторе SHA-256 совпал для пяти снимков из шести. Для Markdown-конфигураций совпали числа токенов и результаты оценок. Второй отчёт сохранён в `target/content-benchmark-public-repeat`.

### Экономия по страницам

Сравнения ниже используют один снимок для обоих преобразований в каждой паре. Медиана даёт одинаковый вес страницам. Для общей экономии суммируются токены `o200k_base` по корпусу.

| Корпус и преобразование | Страницы | Медианная экономия | Общая экономия |
| --- | ---: | ---: | ---: |
| Локальный, Readability перед стандартным Markdown | 30 | 77,90% | 79,50% |
| Публичный, Readability перед стандартным Markdown | 6 | 61,49% | 20,89% |
| Локальный, встроенный Markdown вместо стандартного на Obscura | 30 | −0,51% | −0,26% |
| Публичный, встроенный Markdown вместо стандартного на Obscura | 5 | 5,70% | 5,34% |

В публичном прогоне Readability сократил RFC 9110 на 5,84%. На эту страницу пришлось около 67% токенов стандартного Markdown корпуса. Встроенный Markdown Obscura с тем же входным HTML расходовал на RFC 9110 на 5,13% больше токенов, а на Wikipedia сэкономил 34,56%. На пяти доступных Obscura страницах оба представления прошли одни и те же проверки фактов и структуры. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) · [Wikipedia ISO 8601](https://en.wikipedia.org/wiki/ISO_8601).

В дополнительном эксперименте на синтетическом корпусе удалили точные повторы блоков `nav[aria-label="Site"]` на каждой странице, сохранив первый экземпляр. Для динамических страниц добавили в HTML предусмотренный fixture контент. До удаления токены стандартного Markdown совпали с первой попыткой B. После удаления 96 блоков токены снизились с 4 263 до 1 667, на 60,90%. Ни одна проверка фактов или структуры относительно B не изменилась. Эксперимент измеряет влияние дубликатов, намеренно добавленных в fixtures.

При отдельном прогоне шести публичных страниц в Chromium сравнили `outerHTML` всех блоков `nav` внутри каждой страницы. Среди 28 блоков точных повторов не встретилось. В стандартном Markdown насчитали 7 411 ссылок HTTP(S). После разрешения относительных адресов 2 480 вхождений повторяли URL, уже встречавшийся на той же странице. На RFC 9110 пришлось 2 211 повторных вхождений. Это подсчёт повторов, а экономия токенов зависит от формата представления ссылок. Результаты по страницам находятся в `target/content-benchmark-experiments/nav-on-public.json`.

Отдельно проверили ссылочный синтаксис Markdown `[текст][номер]` с одной записью на повторяющийся исходный адрес. В эксперимент вошли HTTP(S)-ссылки без заголовка и символов, требующих дополнительного экранирования. Оба варианта на каждой странице использовали один HTML-снимок. Результат сравнивали по токенам, размеченным фактам, артефактам и полному HTML после рендера Markdown.

На пяти страницах из шести рендер совпал побайтно. Из них на четырёх вариант экономил токены. На странице Python расход вырос на 10 токенов `o200k_base`. На Wikipedia полное сравнение HTML обнаружило различие, хотя размеченные проверки прошли. При сохранении стандартного представления на этих двух страницах экономия корпуса составила 1,75% по `o200k_base` (242 474 → 238 220) и 1,54% по `cl100k_base` (242 318 → 238 598). RFC 9110 отдельно дал 2,52% по `o200k_base`. Цифры относятся к этому правилу и набору страниц. Протокол сохранён в `target/content-benchmark-experiments/reference-links-public.json`.
