# План улучшения Obeyscura

Утверждён первый этап. Он включает общий конвертер, доступ к исходному HTML и отдельные замеры правил сокращения. Базовая ревизия `76db0c807f4bbaed062fcd3be7760adba49ac841`.

Общий конвертер доступен в ветке `benchmark/structured-markdown`, проверенная ревизия `10a043c`. Локальные проверки структуры выросли с 33/75 до 75/75, расход токенов вырос на 32,26% относительно встроенного Markdown. На публичных страницах сохраняется ошибка готовности W3C WAI. Целевой диапазон экономии пока не достигнут. [Итоговый замер](BENCHMARK.md#итоговый-замер-первого-этапа).

## Основание

На Linux локальные снимки Chromium и Obscura совпали во всех 90 попытках по SHA-256. Встроенный Markdown Obscura сохранил 201 из 201 проверок фактов и 33 из 75 проверок структуры. Стандартный Markdown на тех же снимках сохранил 198 фактов и 57 проверок структуры. Разница в расходе токенов составила 0,26%. Первые кандидаты на улучшение — сохранение кода и семантических блоков и сокращение повторов. [Прямое сравнение](BENCHMARK.md#прямое-сравнение-на-linux) · [аудит](RESEARCH.md).

На шести публичных страницах Chromium Readability сэкономил около 21% токенов и потерял два факта из 17. Obscura подтвердил готовность пяти страниц из шести и сохранил все 14 ожидаемых на них фактов. RFC 9110 составляет около двух третей токенов стандартного Markdown этого корпуса. Точных повторов меню в публичных снимках не встретилось. Ссылочный синтаксис дал 1,75% общей экономии по `o200k_base` на том же наборе при сохранении исходного Markdown на страницах, где вырос расход или изменился рендер. Для оценки правил сокращения сравниваем результаты по страницам и по корпусу целиком. [Публичные замеры](BENCHMARK.md#публичный-корпус).

## Порядок работ

1. **Зафиксировать базовый прогон.** Выполнено в GitHub Actions на release-сборке `76db0c8` с функцией `render`. Набор включает A–D, D-raw, D-standard и X на локальном и публичном корпусах. [Артефакты](https://github.com/JuliossJunk/obeyscura/actions/runs/45704538015).
2. **Сохранить структуру в общем преобразователе.** Модуль получает HTML, исходный URL и данные о захвате. Проверить повторное использование HTML-парсера рабочей области. Сначала покрыть таблицы с объединёнными ячейками, точное содержимое кода, вложенные списки, формулы, раскрываемые блоки, цитаты, сноски и структурированные метаданные. Где Markdown теряет структуру, использовать представление, которое проходит проверку формата, с доступом к исходному HTML. Запуск преобразователя на внешнем снимке позволит измерить E и F с одинаковыми правилами.
3. **Измерить эффект каждого правила сокращения.** На части для разработки проверить компактные разделители, точные повторы блоков и ссылок, избыточную навигацию и декоративные элементы. Проверять случаи с уникальными условиями в подвале и боковой панели. Для каждого правила записывать, какие блоки убраны из выдачи, почему и как их восстановить. Включать правило при парном выигрыше, сохранении размеченных фактов и прохождении структурных проверок. Подбор правил проводить на development. Предварительно выделенную часть evaluation использовать для проверки кандидата.
4. **Подключить оптимизированное чтение к CLI и MCP как опцию.** Сохранить существующие точки входа для текущих клиентов. Добавить к результату идентификатор снимка и способ чтения полного HTML, отдельных разделов, таблиц и ссылок. На лимите возвращать признаки неполноты и курсор. Проверить повторное чтение и ограничение памяти копий снимков. Возможные адаптивный, JSON- и delta-режимы оценивать на сценариях, учитывающих затраты на схемы, восстановление и повторные вызовы.
5. **Повторить бенчмарки и проверить совместимость.** Сопоставить B→E, D→F и D-standard→F на одинаковом корпусе и хосте. Измерить время, CPU, пиковую память, конкурентные сессии и ошибки. Сделать release-сборку, запустить `cargo nextest` для затронутых пакетов и workspace, а также obstacle course с ожидаемыми 33/33. Подключить E и F к workflow сравнений и сохранять отчёты как артефакты CI.
6. **Измерить полную стоимость задач агента.** На размеченных вопросах и заранее выбранных моделях измерить точность, неподтверждённые утверждения, токены сообщений, схем и ответов MCP, дополнительные вызовы, время и стоимость. По мере доступности добавить соответствующие токенизаторы или API для Claude, Gemini, Qwen, DeepSeek и Llama. Использовать совместимость живых сайтов и полную стоимость для выбора движка и необходимости fallback. По итогам обновить документацию и примеры интеграции.

## Предложение для этапа компактного чтения

Первая итерация проверяет оглавление с бюджетом в байтах, идентификатором снимка и курсором продолжения. Чтение по идентификатору раздела возвращает его содержимое из сохранённого снимка. Полный обход по курсорам и команда получения исходного HTML позволяют проверить доступность данных без повторной навигации. Один контракт используется на снимках Obscura и Chromium. По результатам замера можно оценить, стоит ли добавлять содержимое первого раздела в начальную выдачу.

1. Перед реализацией зафиксировать последовательности чтения по существующей разметке корпуса. Включить поиск одного факта, чтение двух разделов, восстановление таблицы с числами и последовательное чтение всего документа. Сохранить существующее разделение `development` и `evaluation`.
2. Сравнить текущую полную выдачу и компактную выдачу на одинаковых по SHA-256 снимках. Учитывать токены оглавления, первого ответа, запросов разделов и всех дочитываний. Отдельно показать число обращений, долю восстановленных фактов и артефактов, медиану по страницам и суммарный результат. Факт засчитывается после получения фрагмента с его текстом или соответствующей ячейкой таблицы.
3. Проверить, что последовательный обход не пропускает блоков и не зацикливается, продолжение явно обозначено при неполной выдаче, а сохранённый HTML совпадает по SHA-256. Ошибки захвата отражать в покрытии корпуса. Проверка с фиксированными обращениями измеряет стоимость интерактивного чтения. Агентский прогон отдельно измерит точность и полный расход контекста модели.

На зафиксированном первом этапе нижняя граница цели (20% экономии) означает до 10 231 токена `o200k_base` вместо текущих 16 959 для 90 локальных пар. Для пяти публичных пар Obscura ориентир составляет до 190 772 вместо 476 901, если сравнивать с D-standard. Это ориентиры для размера выдачи на прежних снимках. Результат по задачам будет включать токены дочитывания. [Замеры первого этапа](BENCHMARK.md#итоговый-замер-первого-этапа).

CLI-итерация `becd503` прошла проверку побайтового восстановления на локальном и публичном корпусах. Целевой раздел на длинных страницах стоил меньше полной выдачи при известном маршруте. На коротком корпусе и при полном обходе оглавление и дочитывания увеличили расход. Следующая проверка с MCP должна показать, как точность выбора раздела, ошибки и стоимость повторных обращений меняют этот результат. [Парные замеры](BENCHMARK.md#сравнение-на-linux).

## Критерии первого релиза

- Целевой диапазон сокращения токенов относительно B составляет 20–50% на общей выборке с успешными захватами. Покрытие всего корпуса и экономия на совместно успешных парах публикуются вместе.
- Полнота значимых фактов ≥99%. Критичные числа и размеченная критичная информация сохраняются полностью. Для тестов восстановления содержимое и ссылки должны читаться по исходному снимку, а у любой неполной выдачи должен быть признак и доступное продолжение.
- Точность агентских ответов сохраняется. Экономия на первой выдаче оценивается с учётом стоимости повторных запросов. Численные итоги сопровождаются количеством попыток и сведениями о конфигурации. [Спецификация](OPTIMIZATION_SPEC.md).
